# Benny automation setup

The original setup, triage, reproduction and bounded-fix procedures remain under automations/benny and the unchanged upstream archive. They are dormant until a real project is configured. A plugin install does not authorize team messages or create schedules.

Supply the repository/default branch, source channel, trusted triage identity, tracker/project, feature map, verification/control surface, available role models, and all eight execution budgets from the template. Reasoning budget is chosen separately by each user. Keep credentials in the host's existing connectors or protected local storage; do not put them in committed configuration or screenshots.

Stage the pack with the native host's file tools or the optional local helper, preserve custom files and resolve conflicts. Review the operational pack and source configuration in the target project before scheduling. Use native agents, current host connectors and the supported scheduler. Optional CLI-specific helper gates are available only with explicitly selected local harnesses; never forge CLI job records for native work.

Validate actual scheduled connector access and obtain explicit authority for a harmless test report. Verify immutable original-thread coordinates, idempotent delivery, trusted markers, two actual reproductions, real media inspection, ownership/rejection gates, a single bounded draft fix and post-fix verification. Test cancellation and recovery. A configured connector name or synthetic message ID is not delivery proof.

Use polling through a supported schedule if inbound events are unavailable. Do not create a public event receiver, tunnel or laptop relay. Workers must not receive posting credentials; the authorized coordinator owns external writes. Keep schedules dormant until these acceptance criteria pass. Live team delivery and actual cloud scheduling remain tracked gaps.
